# HIT PARADE - ONLINE PVP NETCODE

Lane: netcode (2026-09-29, US Central evening; probe timestamps are UTC 2026-09-30T02:17-02:33).
Scope: online 1v1 PVP for a 60 Hz deterministic fighting sim on the existing ForgeFlow stack (NetPlay over
Supabase Realtime), with latency MEASURED on the live relay.

Labels used below: **[measured]** = a number from a probe run this session (file named);
**[source]** = read in code this session (file:line or URL); **[cited]** = a web source (URL);
**[estimate]** = arithmetic on stated assumptions; **[design]** = a decision this document makes.

## Outcome in six lines

1. **The Supabase relay cannot carry a 60 Hz rollback input stream.** A 1v1 at 60 Hz both ways spends
   240 events/s, which is 2.4x the free plan's 100 events/s. That cap is for the WHOLE project (every FFG online game;
   `games/` holds 15 NetPlay copies), measured as a 60 s rolling average, and exceeding it closes every live
   channel on the project [source + cited, section 0.3].
2. **Relay latency from this machine** [measured, 4 full runs + 1 quick run]: RTT median 84-191 ms per 60 Hz
   burst (pooled over the 4 full runs: median 145.6, p90 241.3, p99 327.7, max 387.2 ms, n=800). Out of 2,340 pings
   there was 0 loss and 0 duplicates. **1.88% of burst messages arrived out of order** (60 of 3,200), so
   Broadcast is not strictly ordered. There was no throttling at 60 Hz ping plus 60 Hz pong.
3. **Transport** [design]: inputs go over **WebRTC DataChannel P2P** (`ordered:false, maxRetransmits:0`, Google STUN,
   no TURN) at 60 Hz. Supabase keeps the lobby, the room, signalling and match control. **Relay fallback** is
   used only when ICE fails: 10 Hz batched binary packets with input delay D=4 and a 12-frame rollback
   window, at most ONE relayed HIT PARADE match at a time project-wide.
4. **Rollback core** [design]: GGPO model: input delay D = clamp(ceil(RTT/2/16.67) - 3, 1, 4) on P2P, an 8-frame
   rollback window (GGPO `MAX_PREDICTION_FRAMES 8`), every packet carries all un-acked inputs, time sync,
   checksum every 15 confirmed frames, and a host snapshot on desync. The sim state is one Int32Array of 4 KB or less:
   save 0.113 us, restore 0.078 us, checksum 1.9 us [measured]. structuredClone of an equivalent object is
   215.6 us, which is ~1,900x slower.
5. **Trace-driven model on the measured relay traces** [measured input, model output]: at 60 Hz with D=3 and W=8,
   game speed was 96.5-100% (stalls 0-3.6%). As the fallback with 10 Hz, D=4 and W=12, speed was 98.0-100%, with
   a median prediction depth of 2-7 frames. Direct P2P should be no worse than the 60 Hz relay rows in the same
   region [inferred, not measured].
6. **Write our own** rollback (~1 kLOC TS estimate). The browser libraries found are unmaintained or
   archived, or they bring their own servers/frameworks (section 2.5). Section 7 lists the owner and cross-lane items:
   TURN spend, portfolio DoS exposure, the `eventsPerSecond` myth, three determinism conflicts in
   `TECH_REUSE.md`, and the limits of this measurement.

### 0.3 Rate limits and throttling [measured + source + cited]

- **No throttle signal in any run** (no `CHANNEL_ERROR`, no `Too many messages per second`, no heartbeat errors
  before teardown). The quick-run JSON lists two `CLOSED` entries: they are its own teardown, and that run predates the
  teardown filter.
- **Why nothing fired, and what the real ceiling is** (read in `supabase/realtime` main this session):
  - `lib/realtime/tenants.ex` `events_per_second_rate/2`: `tick: :timer.seconds(5)`, `max_bucket_len: 12`,
    `measurement: :avg`, keyed by `events_per_second_key(tenant_id)`. That is **one counter per project: a 60 s rolling
    average**. It averages over fewer buckets for the first minute after the counter process starts (it idles out after
    5 min, `rate_counter.ex @idle_shutdown`), so a burst on a cold counter weighs more. This is the `main` branch; the
    hosted build may lag it.
  - It is incremented once per inbound broadcast (`broadcast_handler.ex` `increment_rate_counter`) and once per
    delivery to each subscriber (`message_dispatcher.ex` sends `:update_rate_counter` per subscriber ->
    `realtime_channel.ex:301-302` `count(socket)`).
  - When the average is at or above the limit, the next `:update_rate_counter` on ANY channel of the project runs
    `shutdown_response(socket, "Too many messages per second")` (`realtime_channel.ex:301-311`). It stays
    triggered until the 60 s average falls back under the limit (`rate_counter.ex` `maybe_trigger_limit`).
  - Free plan: **100 messages/s per project**, 200 concurrent connections, presence 20 msg/s, broadcast payload
    256 KB [cited: https://supabase.com/docs/guides/realtime/limits]. "Channels that exceed the average are
    closed with `Too many messages per second`, which `supabase-js` recovers from by rejoining"
    [cited: https://supabase.com/docs/guides/realtime/settings]. Billing: "one message sent plus one message per
    subscribed client that receives it" [cited: https://supabase.com/docs/guides/platform/manage-your-usage/realtime-messages].
    Free quota 2M messages/month [cited: https://supabase.com/docs/guides/realtime/pricing].
- **Throttle onset, derived**: a 1v1 where each peer sends R msg/s costs **4R events/s** (2 senders x (1 send + 1
  delivery)). With zero other traffic on the project, **R_max = 25 Hz per peer, sustained over 60 s**. A 60 Hz stream
  both ways is 240/s. The probe's 60 Hz ping plus 60 Hz pong was 240/s **instantaneous** for 3.3 s and did not trip,
  because the limiter averages over 60 s. I did **not** push past the ceiling on purpose: the limiter is
  project-wide, so overshooting would have closed every live room in every FFG game for up to about a minute. Worst 60 s
  window per full run: one burst (800 events) plus the preceding 2 Hz or 1 Hz traffic, about 17-21 events/s. The quick run put both bursts in one
  window: about 43 events/s if the counter was cold.
- **`eventsPerSecond` is a no-op** [measured + source]. Client A declared `params: { eventsPerSecond: 1 }`, and every
  60 Hz burst still delivered 200/200. The server's `user_socket.ex connect/3` reads only `apikey`/access token and
  `log_level` from params. A search for `eventsPerSecond` (and for `throttle`) finds nothing in realtime-js 2.103.2 (`dist/main`), the live
  2.117.2 bundle from esm.sh, or the Phoenix client it imports (`@supabase/phoenix` 0.4.0 local, 0.4.5 live). The claim in `games/last-circle/runtime/net/ffg_netplay.js:43-54` that the
  server "rate-limits the connection to it" is therefore false today, and the 12-vs-30 "drift" discussed in
  `blackridge/_design/expansion/netcode.md` §1.4 changes nothing on the wire. The real limit is the project average above.
- **Cost of this measurement**: 11,080 events in total (1,720 quick + 4 x 2,340) [measured, `tenant_events_spent_est`], about
  0.55% of the 2M monthly quota. $0.

  + "_" + random` (line 30), and the lexically lowest id is host. Quick match: presence in `ffg-lobby:<gameId>`,
  the two lowest ids pair into room `(a.slice(-4)+b.slice(-4)).toUpperCase()` (line 91), join the room first, and
  linger 4 s in the lobby (lines 93-101). The `peer` event fires only on the 1<->2 boundary in the base copy.
  Last-circle's copy also fires on count change.
- **Ember Sanctum's real-time online duel** (source outside the repo: `F:/GrokUI/projects/default/src/online.js`,
  230 lines; `netplay.js` 148 lines, the same NetPlay with `eventsPerSecond: 30`). It is NOT deterministic. `OnlineRival`
  interpolates a **15 Hz state stream** `{x,z,f,hp,hpMax}` (`setInterval(..., 66)`, online.js:188-200) with
  `k = 1 - exp(-12 dt)` smoothing. Authority is the **victim applies hits** (`"hit" {dmg,crit}` ->
  `_takeOnlineHit`), and the dier broadcasts `"down"` so both sides score the round from a single source. Bo3
  sides are deterministic, the host picks the arena at random and sends `"start"` 1.2 s after HELLO, and
  presence-loss while live means "duel void". This works for a hack-and-slash but **cannot give fighting-game
  fidelity**: at the measured ~62-86 ms relay one-way medians, plus 66 ms of snapshot spacing, plus smoothing,
  the opponent is drawn ~150+ ms in the past and every hit is decided on the victim's screen.
- **WebRTC precedent**: `games/last-circle/runtime/net/ffg_rtc.js` (107 lines) `RTCMesh`: signalling rides the
  room channel (`{t:"rtc", d:{to, kind, sdp|cand}}`), the lower id offers (no glare), Google STUN only, no TURN,

- **Test doubles**: `games/chroma-hide/runtime/net/loopback.js` (in-process hub using the real pack/unpack).
  **Ratings**: `pipeline/engine/runtime/net/ffg_ratings.js` (`report_match_result` RPC, Elo, idempotent by

- **Budget code already in the portfolio**: `last-circle/runtime/3d/royale/net.js:123-143` `sendBudgetLeft()` =

## 2. Research (cited)

### 2.1 Supabase Realtime free tier
See 0.3 for the limits table and enforcement. Consequences for HIT PARADE:
- **Concurrent connections 200 per project** [cited limits page]. Each online player holds one socket for
  lobby/room/presence, so HIT PARADE competes with every other FFG game for those 200.
- **2M messages/month**. A P2P match costs only lobby + room + signalling + control traffic: roughly 60 sends ->
  ~120 events per match [estimate], so ~16k matches/month. A 3-minute relayed match at 10 Hz costs 40 events/s x
  180 s = 7,200 events [estimate], so ~277 relayed matches/month if nothing else used the project.
- **Presence limit 20 msg/s** (free). Lobby presence diffs fan out to every lobby member, so a big quick-match queue
  is itself a rate risk. Keep the lobby small (pair fast, leave fast).
- **Private channels / authorization** exist (`config: { private: true }`, RLS on `realtime.messages`, and "disable
  the 'Allow public access' setting") [cited: https://supabase.com/docs/guides/realtime/authorization]. Today every
  FFG game uses public channels with one shared anon key (section 7, item 2).

### 2.2 GGPO-style rollback
- The model: **input delay** schedules local input X frames ahead; **prediction** runs the sim with the remote's last
  known input; **rollback** restores the last correct state when a real input disagrees and re-simulates to now
  [cited: https://github.com/pond3r/ggpo/blob/master/doc/README.md, https://www.gamedeveloper.com/programming/the-lag-fighting-techniques-behind-ggpo-s-netcode].
- Hard requirements [cited: GGPO DeveloperGuide
  https://raw.githubusercontent.com/pond3r/ggpo/master/doc/DeveloperGuide.md]: "The game simulation must be fully
  deterministic"; `save_game_state` / `load_game_state` / `advance_frame` callbacks; the RNG seed must be equal at
  frame 0 and "the state of the random number generator is included in your game state"; SyncTest "will execute a 1
  frame rollback for every frame of your game" and compare checksums. Use it continuously.
- Constants from the GGPO source [source, fetched this session]: `GGPO_MAX_PREDICTION_FRAMES 8`
  (`ggponet.h:34`); saved-frame ring `MAX_PREDICTION_FRAMES + 2` (`sync.h:74`); time sync `FRAME_WINDOW_SIZE 40`,
  `MAX_FRAME_ADVANTAGE 9` (`timesync.h`), `RECOMMENDATION_INTERVAL 240` (`p2p.cpp:10`); input packets carry
  **every pending un-acked input** from `start_frame` and are trimmed by `ack_frame` (`udp_proto.cpp:118-127, 617`);
  `KEEP_ALIVE_INTERVAL 200` ms, `QUALITY_REPORT_INTERVAL 1000` ms, 5 sync round trips before running
  (`udp_proto.cpp:13-18`); `DEFAULT_DISCONNECT_NOTIFY_START 750` ms, `DEFAULT_DISCONNECT_TIMEOUT 5000` ms
  (`p2p.cpp:11-12`). Licence MIT (`LICENSE`).
- The CPU budget is real: NetherRealm's GDC 2018 talk is titled "8 Frames in 16ms: Rollback Networking in Mortal Kombat
  and Injustice 2" [cited: https://www.gdcvault.com/play/1025471/8-Frames-in-16ms-Rollback].

### 2.3 WebRTC DataChannel, STUN, no TURN
- `ordered:false` lets messages arrive out of order; `maxRetransmits` caps retransmits "in unreliable mode"
  [cited: https://developer.mozilla.org/en-US/docs/Web/API/RTCPeerConnection/createDataChannel]. With
  `maxRetransmits:0` and redundant inputs in every packet, a lost packet costs nothing.
- **Failure rate without TURN**. There is no single authoritative number. Tsahi Levent-Levi on discuss-webrtc: "Most large vendors I've
  spoken to report 20% TURN relay traffic. Some reported over 30%". The thread cites callstats.io at 30% [cited:
  https://groups.google.com/g/discuss-webrtc/c/5d_EJwM6iJM]. bloggeek gives a range of 0-50% depending on user base
  [cited: https://bloggeek.me/webrtcglossary/turn/]. forasoft gives "roughly 15-20% of consumer WebRTC sessions need
  TURN" and notes that symmetric NAT, which a meaningful share of carrier-grade NATs behave as, is what breaks STUN [cited:
  https://www.forasoft.com/learn/video-streaming/articles-streaming/nat-stun-turn-ice-webrtc]. **Planning figure:
  15-30% of pairs will not connect P2P** [estimate from the cited range], higher on mobile data. They need the relay
  fallback.
- **TURN is not free**: Cloudflare Realtime TURN is "free of charge when used together with the Realtime SFU.
  Otherwise, it costs $0.05/real-time GB" [cited: https://developers.cloudflare.com/realtime/turn/]. See section 7, item 1.
- **Supabase as signalling**: already proven in the portfolio (last-circle `RTCMesh`: offer/answer/ICE over the room
  channel). For 1v1 that is roughly 1 offer + 1 answer + about 5-15 trickle candidates per side [estimate], a few dozen
  broadcasts per match.

### 2.4 Determinism facts for JS
- ECMA-262 §21.3.2: "The behaviour of the functions acos, acosh, asin, asinh, atan, atanh, atan2, cbrt, cos, cosh, exp,
  expm1, hypot, log, log1p, log2, log10, pow, random, sin, sinh, tan, and tanh is not precisely specified here…"
  [cited: https://tc39.es/ecma262/multipage/numbers-and-dates.html]. Note that `pow` (and so `**`) is on the list. These can differ across browsers/CPUs, so they are
  banned in the sim. `+ - * /`, `Math.sqrt`, `Math.imul`, `Math.trunc/floor` are exactly specified (IEEE-754 /
  integer semantics).

## 3. Protocol design [design unless labelled]

### 3.1 Transport tiers
| tier | carries | channel | rate |
|---|---|---|---|
| T0 lobby | quick-match presence | Supabase `ffg-lobby:hit-parade` | presence only |
| T1 room / control | HELLO, char-select commit/reveal, stage/seed, RTC signalling, START, RESULT, REMATCH, BYE | Supabase `ffg:hit-parade:<CODE>` until RTC is up, then DataChannel `ctl` | a few msgs per phase |
| T2 inputs (P2P) | INPUT packets, 60 Hz, binary | DataChannel `in` `{ordered:false, maxRetransmits:0}` | 60 Hz each way |
| T2' inputs (fallback) | the same INPUT packets batched every 6 frames | Supabase room channel, binary broadcast (event `i`) | 10 Hz each way = 40 events/s |
| ctl (P2P) | control + desync snapshot | DataChannel `ctl` `{ordered:true}` (reliable) | rare |

- A vendored **per-game NetPlay copy** (`runtime/src/net/netplay.ts`) with: last-circle's count-change `peer` event, a
  **6 s** lobby linger (0.5), protocol + build version in presence meta, and the `eventsPerSecond` param dropped, with a
  comment citing 0.3.
- **RTC**: adapt `ffg_rtc.js` to 1:1. Lower peer id offers. `iceServers`: `stun:stun.l.google.com:19302`,
  `stun:stun1.l.google.com:19302`, `stun:stun.cloudflare.com:3478` (all three answered in 0.5). There are two channels,
  `in` and `ctl`, and `binaryType='arraybuffer'`. After open, read `getStats()` for the selected candidate pair (host / srflx /
  prflx) and log it with the match.
- **Fallback trigger**: ICE not `connected` with both channels open within **5 s** of the offer, or the `in`
  channel is silent for 5 s mid-match (GGPO's disconnect timeout) while Supabase presence still shows the peer. Then:
  1. Check relay capacity: presence on `ffg-relay:hit-parade`. If a relayed match is already tracked, don't
     start a second one. Show "Direct connection failed and the backup line is busy" and offer re-queue.
  2. Otherwise track, switch to T2', and set D=4, W=12 (0.7). An ICE restart keeps trying in the background, and the
     match swaps back to P2P between rounds if it opens.
- **Why the relay stays at 10 Hz and single-match**: 40 events/s is 40% of the whole project's cap. Two relayed matches plus
  any other game's traffic could trip the project-wide limiter and knock every FFG game offline (0.3).

### 3.2 INPUT packet (binary, little-endian) - identical on both transports
```
off size field
0   u8   type = 0x01 (INPUT)
1   u8   flags: b0 relay, b1 has-checksum, b2 pause-request, b3 i-am-stalled
2   u16  seq              packet counter (loss/reorder stats)
4   u32  startFrame       sim frame of the first input word below
8   u32  ackFrame         highest remote input frame received contiguously (sender trims up to it)
12  i8   frameAdvantage   local frame - estimated remote frame (time sync, clamped +-127)
13  u8   count N          1..32 input words
14  u16  tsLow            sender ms clock & 0xffff        } continuous RTT:
16  u16  echoTs           last tsLow received from peer   } rtt = now - echoTs - echoHold
18  u16  echoHold         ms between receiving echoTs and sending this packet
[20 u32  csFrame, 24 u32 checksum]   only when flags.b1 (confirmed-frame checksum)
then N x u16 input words (frames startFrame .. startFrame+N-1)
```
- Size: 20 B + 2N (+8 with a checksum). A typical N of 6-10 gives 32-40 B on P2P. On the relay the frame overhead is the topic
  (0.4), and bytes don't matter because events are the billed unit.
- **Redundancy**: every packet repeats every input the peer hasn't acked (GGPO `pending_output`), capped at 32
  (0.53 s). This absorbs loss and the measured 1.88% reordering. The receiver keeps the first value it sees for a frame.
- **Input word (u16)**: b0-3 U/D/L/R **after SOCD cleaning** (L+R -> neutral, U+D -> U), done before packing so both
  peers see the same word; b4 LIGHT, b5 HEAVY, b6 SPECIAL, b7 GRAB, b8 BLOCK, b9 DODGE, b10 TAUNT, b11-15 zero.
  Left/right stay raw: forward/back is derived inside the sim from sim-side facing.
- Receive validation: `len == 20 + 8*b1 + 2N`, `1 <= N <= 32`, `startFrame + N - 1 <= localFrame + D + W + 32`. A
  frame that is already confirmed must carry the **same** value it did before; a mismatch is a protocol violation (3.9).

### 3.3 Input delay by RTT
- RTT comes from the sync phase (3.6): the median of 10 DataChannel ping/pongs taken **after a 1 s settle** (0.5), then kept
  up to date continuously from `tsLow/echoTs/echoHold`.
- `F = ceil((RTT_median / 2) / 16.667)` one-way frames. **P2P: `D = clamp(F - 3, 1, 4)`.** **Relay: `D = 4`.**
  Both peers compute it, and the host's value is authoritative (sent in START). D is **fixed for a round** and may change
  only during the between-round freeze, so execution timing never shifts mid-exchange.

| RTT | F | D (P2P) | one-way hidden by rollback (F - D frames) |
|---|---|---|---|
| 30 ms | 1 | 1 | 0 |
| 60 ms | 2 | 1 | 1 |
| 100 ms | 3 | 1 | 2 |
| 150 ms | 5 | 2 | 3 |
| 200 ms | 6 | 3 | 3 |
| 250 ms | 8 | 4 | 4 |
| 330 ms | 10 | 4 | 6 |
| > 400 ms | > 12 | 4 | > W, so stalls (0.7) |
- Why "-3": the model (0.7) shows median depth of 1-3 frames at D=2-3 on 46-97 ms one-way traces, and that is the
  feel target (small, frequent corrections hidden inside hit-stop and move start-up). D_min=1 absorbs sampling jitter
  for a near-invisible 16.7 ms. The build's netsim harness (section 6) re-tunes the constant against the traces.
- **Matchmaking soft cap**: quick match shows RTT after pairing. Above 200 ms it warns, and above 300 ms it offers "find
  another opponent" before character select. Private rooms always allowed.

### 3.4 Rollback window, time sync, stalls
- **W = 8 frames on P2P** (GGPO `MAX_PREDICTION_FRAMES 8`); **W = 12 on relay** (0.7). If prediction depth would
  exceed W, the sim **does not advance that frame** (a stall). The HUD shows a connection-quality icon, never a freeze
  overlay for a single frame.
- **Time sync**: each packet carries `frameAdvantage`. Every 240 frames (GGPO `RECOMMENDATION_INTERVAL`), if my mean
  advantage exceeds the peer's by 2 or more frames, I skip `floor(diff/2)` frames spread one per 20 frames (cap 9, GGPO
  `MAX_FRAME_ADVANTAGE`). This keeps both peers equally far into prediction instead of one side eating all the
  rollbacks.
- **Rendering under rollback**: the view renders only the latest simulated state. Sim events (hit, block, KO, sfx
  cues, particles) carry `(frame, kind, actorSlot, seq)`. The view keeps a ledger, fires each event once, and on rollback
  cancels events that no longer exist (long SFX stop, short ones play out) and fires new ones.

### 3.5 Save / restore budget and state rules
- **All sim state lives in ONE preallocated `ArrayBuffer` viewed as `Int32Array`: target 2 KB, hard cap 4 KB.** At 4 KB:
  save 0.113 us, restore 0.078 us, mix32 checksum 1.93 us [measured, 0.6]. A ring of W+2 slots (10 P2P, 14 relay), the
  GGPO ring shape.
- Per-frame netcode overhead budget: save + (occasional) checksum **<= 10 us** desktop. Measured: ~2 us.
- **Sim step budget: <= 0.25 ms desktop** (Node probe), so a worst-case 12-frame resim plus restore fits in ~3 ms of a 16.7
  ms frame. Phones: plan on ~4x slower [assumption, to verify in the mobile harness]. If a device misses the frame
  budget, the net layer raises D by 1 (fewer rollbacks) rather than dropping frames.
- `structuredClone` / JSON snapshots are banned in the hot path (215.6 / 154.8 us, 0.6).
- A memory layout contract: every field has a fixed word offset declared in one `layout.ts`. Adding a field bumps
  `STATE_VERSION`, which is part of HELLO.

### 3.6 Match flow
1. **Online menu**: QUICK MATCH / CREATE ROOM (8-char code) / JOIN ROOM (code, and a `?room=CODE` deep link like
   last-circle). Quick match = NetPlay lobby pairing (6 s linger).
2. **Room**: presence shows both. HELLO `{proto, VERSION, dataHash, stateVersion, name, rated?}`. Any mismatch in
   `proto/VERSION/dataHash/stateVersion` gives "Your opponent is on a different version - refresh", and no match.
   **Only the first two presence ids** (lowest peer ids) are players. Anyone else is ignored.
3. **RTC up** (5 s budget, 3.1). **Sync**: wait 1 s after both channels open (0.5 shows first-second outliers up to
   788.8 ms), then 10 ping/pongs -> RTT -> D. On relay, 5 ping/pongs over the room channel (GGPO uses 5 sync round trips).
4. **Character select (30 s, NetPlay `TurnClock`)**: simultaneous and blind via **commit-reveal**. Each side sends
   `SHA-256(fighterId | colour | salt)` (WebCrypto); once both commits arrive, both reveal and each verifies. Nobody can
   counter-pick off the other's packet. A timer expiry picks the cursor's fighter.
5. **Stage + seed**: each side commits a random u32 the same way. `seed = hash32(seedLow, seedHigh)` (dyefield
   `rng.ts hash32`). Game 1 stage = `seed % stageCount`. Rematch: the loser picks the stage (SF convention). Host sends
   `START {seed, fighters[2], stage, D, W, rules:{rounds:3, timer:99}, startInMs:1500}`. The guest starts at `recv +
   1500 - RTT/2`, the host at `send + 1500`.
6. **Match**: inputs only. KOs, time-outs, round and match results are **sim outputs**, so there is no "down"/"end" message
   (unlike ember-sanctum's victim-authority model).
7. **Result**: both show the sim's result. RESULT `{matchId, winnerSlot, finalFrame, finalChecksum}` crosses peers,
   and agreement is required before either reports to `report_match_result` (ratings only when both are logged in;
   `matchId = hash(roomCode, matchIndex, seed)`).
8. **Rematch**: both press REMATCH within 20 s. The loser may change fighter first (commit-reveal again). Otherwise
   back to the menu with BYE.

### 3.7 Desync detection and recovery
- When a frame becomes **confirmed** (all inputs up to it are real) and `frame % 15 == 0` (every 250 ms), checksum that
  ring slot (mix32) and ride it on outgoing packets (`flags.b1`) until acked. The receiver compares against its own
  checksum ring (64 entries).
- **Mismatch** gives DESYNC. The host (lower peer id) sends a binary **snapshot of its last confirmed frame** (at most 4 KB, `ctl`
  channel; on relay, a Supabase broadcast, far under 256 KB). The guest loads it, replays known inputs to the present,
  and both continue. Both dump `(frame, both states, input log)` to the dev report. A desync is a determinism bug, and
  the fix is in the sim, never a tolerance.
- More than 2 desyncs in one match: end as NO CONTEST (unrated) and file the report.

### 3.8 Disconnects
- `in` silent for **750 ms** (GGPO notify start) -> "CONNECTION UNSTABLE" strip (the sim is already stalling at W).
- **5 s** silent -> try the relay (3.1) while presence still shows the peer.
- **Peer presence gone** from the Supabase room (tab closed / navigated) -> 10 s reconnect grace (same peer id may
  rejoin, get a snapshot + input history, and resume), then **the leaver forfeits** (ranked: counted as a loss for the
  leaver; unranked: win shown).
- **No data but presence present for 20 s** (a network problem, not a quit) -> NO CONTEST, unrated.
- **Tab hidden**: browsers stop rAF in hidden tabs, so the local sim halts and the peer stalls. On `visibilitychange`
  send `pause-request` (`flags.b2`). The peer shows "OPPONENT AWAY 10 s", then applies the presence-gone rule.
  Online matches have no pause menu (fighting-game convention). The local pause key opens settings without stopping the sim.

### 3.9 Anti-abuse basics
- **Nothing is hidden in a 1v1 fighter**, so the P2P model leaks nothing useful. Inputs are the whole truth.
- **Frozen past**: a confirmed input can never change. A peer that resends a different value for a confirmed frame is
  cheating or broken, so NO CONTEST and log it. Inputs are accepted only inside the window (3.2 validation), so a "lag switch"
  can only stall both players. It cannot rewrite the past, and a stall longer than the 5 s / 20 s rules above ends the match.
- **Results are sim-derived**, and both RESULTs must match before any rating report. The RPC is idempotent by match_id (per
  its header). A P2P client can still refuse to report, so ratings stay "trust but verify" [known limit].
- **Room hijack**: 8-char codes (36^8 = 2.8e12). A third presence is ignored. HELLO carries a random session token that
  every later control message must echo.
- **Commit-reveal** for picks and seed (3.6) stops counter-pick and seed grinding.
- **No free text chat**: preset taunts only, so no moderation is needed.
- **Relay courtesy**: the relay path self-limits to 10 Hz and one match (3.1). Inputs never go to Supabase at 60 Hz.

## 4. Determinism rules the sim MUST follow [design; enforced by the SyncTest probe in section 6]

1. **THREE-free, DOM-free, clock-free core** (`runtime/src/core/sim/**`) runs the same in Node and the browser. The sim
   step signature is `step(state: Int32Array, in0: number, in1: number): void`. Slot 0 = P1 = host, slot 1 = P2. The
   words "local" and "remote" never appear in sim code.
2. **Integers only in the sim**: fixed point with positions in 1/1000 m (mm) and velocities in mm/frame (int32). A
   multiply that can exceed 2^31 uses a helper that asserts `|a*b| < 2^53` in dev builds, then `Math.trunc(a*b/SCALE)`.
   Division is `Math.trunc(a/b)`. **No floats are stored in state.**
3. **Banned in the sim**: `Math.random`, `Date`, `performance.now`, timers, `Math.sin/cos/tan/atan2/exp/log/pow/**`,
   `hypot`, `cbrt` (ECMA-262 §21.3.2 leaves them implementation-approximated, 2.4). Angles, if any, use a build-time
   integer sine table (4096 entries, generated once, committed as data). Distance checks compare squared integers.
   `Math.sqrt` is allowed only on integers when unavoidable (it is correctly rounded).
4. **RNG state lives in the state buffer**: a mulberry32 step on a state word (the algorithm from dyefield
   `core/rng.ts`, but **not its closure**, because a closure's hidden `a` is not saved or restored by rollback). Integer
   outputs only (`>>> 0`, then range by `Math.imul`-high-bits or `%`). Seeded from the START seed.
5. **Fixed iteration order**: fixed-size slot arrays (fighters `[0,1]`, projectiles `[0..7]`, hazards `[0..n]`) walked by
   index. No `Map`/`Set`/object-key iteration, and no `Array.prototype.sort` without a total-order comparator.
   Simultaneous events resolve by rule, never by processing order: same-frame hits trade (both apply), throw vs
   throw is a tech, and ties use slot 0 before slot 1 only where the rule is symmetric.
6. **Hit-stop, super-freeze, slow-mo and KO slow-down are sim frame counters.** The app loop's `timeScale` must stay 1.0
   in online (and ideally everywhere). Presentation may ease the camera, but the sim steps exactly one frame per network
   frame (section 7, item 4).
7. **Animation never drives gameplay**: hitboxes, hurtboxes, root motion and cancel windows come from frame-data tables
   (`data/moves.json`, integers per frame), generated at build time from the clips. The sim never samples a skinned
   mesh or bone.
8. **Gameplay-relevant settings are match rules or fixed online**: hit-stop scale, control scheme / assist inputs, and
   handicap are exchanged in START or forced to defaults. Cosmetic settings (gore/sparks/confetti, camera shake,
   reduced flashing) stay local.
9. **Data identity**: fighters/moves JSON are converted to Int32 tables at boot. `dataHash` (a hash of those tables) and
   `STATE_VERSION` go in HELLO, and a mismatch means no match.
10. **No leaky state**: anything that affects a future frame lives in the buffer (input buffers for motion inputs,
    combo counters, juggle decay, meter, timers, RNG, round state, stage hazard phase). The view may cache, but it never
    feeds back.
11. **Fixed step**: the loop's accumulator only decides how many steps to run. Online, the net session decides
    (advance / stall / resim). The sim never sees wall-clock dt.

## 7. Findings for the owner / other lanes (out of scope here, not acted on)
1. **TURN spend (owner gate, $ > 0)**. Without TURN, roughly 15-30% of pairs fall back to the relay (2.3), which is capped
   at one match at a time. Cloudflare TURN is $0.05/GB. A P2P input stream is about 60 packets/s x ~120 B with headers,
   ~7 KB/s per direction [estimate], so about 2.6 MB per 3-minute match, **about $0.00013 per relayed match**
   [estimate]. It needs a tiny credential-minting endpoint (for example a Pages Function) because the TURN key can't ship in the
   client. Recommendation: ship without TURN, measure the fallback rate from the logged candidate-pair types, and
   decide with data.
2. **Portfolio DoS exposure (pre-existing)**. Anyone holding the public anon key can broadcast on any `ffg:*` channel.
   Sustained traffic over 100 events/s closes **every** live channel in every FFG game (0.3). The real fix is Realtime
   Authorization / private channels plus disabling public access (2.1), which touches all 15 NetPlay copies, so it's an
   owner decision.
3. **The `eventsPerSecond` comment in `games/last-circle/runtime/net/ffg_netplay.js:43-54` is wrong** (0.3). So is
   royale/net.js's per-connection "100/H" framing: the 100 is per PROJECT, so Last Circle's budget should count other
   games' traffic too. Worth a doc fix in those files by their lane.
4. **Cross-lane determinism conflicts in `_research/TECH_REUSE.md`**:
   - Line 13 / table row 6 reuses blocktooth's loop `timeScale` "for hit-stop and slow-mo". In a rollback game those
     must be sim frame counters (rule 4.6). TECH_REUSE line 159 already puts "sim-side hitstop ticks" in `sim/hits.ts`,
     so the loop row should say timeScale is presentation-only and 1.0 online.
   - Line 64 adds a per-player `hitStopScale` setting. Online, that is a desync source unless it is a match rule or
     fixed (rule 4.8).
   - blocktooth's `SIM_HZ = 30` (`src/core/config.ts:104`). HIT PARADE's sim must be 60 Hz.
5. **Measurement limits (fidelity)**: one vantage point (DFW), five runs over ~15 minutes, and the relay latency swung
   (RTT medians 84-191 ms). No real two-city P2P RTT was measured, because that needs two real remote peers. The first live
   2-tab/two-device test (gate N6) should log RTT and the candidate-pair type to close this.
