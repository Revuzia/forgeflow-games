### [audio] Menu music never plays on a cold load — the 4.9 MB track downloads and is silently discarded by the autoplay policy, with no gesture retry anywhere
- **at** `runtime/3d/royale/audio.js:50`
- **why** On every cold load the player sits on the main menu in total silence. `new Audio().play()` before any user gesture rejects with NotAllowedError in Chrome, Edge, Safari and Firefox; the `.catch(() => {})` swallows it with no console trace, so the failure is invisible. The browser still fetches assets/audio/music_menu.mp3 (4,900,350 bytes, verified via `ls -la assets/audio/`) — 4.9 MB of bandwidth burned on a track that is never heard. Match music works by accident only because startMatchMusic (ffg_royale3d.js:280) runs after the player has clicked PLAY and the page has sticky activation. The menu is the first impression and it is the one screen guaranteed to be silent.
- **fix** Retain the pending element and retry it from the existing gesture handler. In playTrack, after the failed play, leave `musicEl` assigned (it already is). Then change audio.js:175 to: `window.addEventListener("pointerdown", () => { ensureCtx(W); if (ctx.state === "suspended") ctx.resume(); if (musicEl && musicEl.paused) { const p = musicEl.play(); if (p && p.catch) p.catch(() => {}); } }, { once: false });` and add the identical listener for "keydown" (a player who tabs/enters through the menu never fires pointerdown). Optionally gate the 4.9 MB fetch behind the first gesture too by setting `musicEl.preload = "none"` until the retry.
- **vs benchmark** Final Drop and every CrazyGames title start menu music on the first click/keypress rather than dropping it — the standard pattern is a one-shot 'audio unlock' handler that flushes any queued track. AAA BRs (Fortnite lobby, Apex menu) treat lobby music as part of the identity of the front-end; shipping a silent menu while paying full download cost for the track is strictly worse than not having the track.

### [audio] Touching ANY volume slider makes music jump ~1.8× louder — setVolumes drops the per-track volume multiplier that playTrack applied
- **at** `runtime/3d/royale/audio.js:38`
- **why** With the shipped defaults (ffg_royale3d.js:392 `masterVol: 0.8, musicVol: 0.5`) match music plays at 0.55 × 0.5 × 0.8 = 0.22. The instant the player nudges any slider — including the SFX slider, which should not touch music at all — it is rewritten to 0.5 × 0.8 = 0.40. That is 1.82×, +5.2 dB, an unmistakable jump mid-match. The failure mode is perverse: a player who opens settings because the music is too loud and drags Music down from 0.5 to 0.45 gets 0.45 × 0.8 = 0.36, which is still 64% LOUDER than what they were just listening to. The slider appears to do the opposite of what it says.
- **fix** Store the per-track trim so both paths use it. Add a module-level `let musicTrim = 1;`, set `musicTrim = (vol != null ? vol : 1);` in playTrack before line 47, and change audio.js:38 to `if (musicEl) musicEl.volume = musicTrim * W.settings.musicVol * W.settings.masterVol;`. Also guard the SFX slider from re-touching music at all — but the shared multiplier fix makes that harmless either way.
- **vs benchmark** A per-track mastering trim that is applied at start and dropped on every subsequent volume update is a mixer bug no shipped game has; Final Drop and AAA titles bake the per-cue trim into the cue definition so the slider is a pure multiplier on top of it. The user-facing rule this violates is universal: moving a volume slider must be monotonic and must only affect its own bus.

### [progression-meta (XP, levels, unlocks, skins, career persistence, challenges, retention hooks, unlock ceiling)] Survival XP, the 'Survived' stat, and lifetime timeAlive all measure MATCH length, not how long you lived — spectating a corpse pays XP
- **at** `runtime/3d/royale/hud.js:2080`
- **why** Death does not stop the clock — killActor (player.js:1093) puts the player into spectate and the frame loop keeps incrementing W.t until endMatch. The code already knows this: the comment at hud.js:1441 says so verbatim, and the challenge loop was guarded with `W.player.alive`. The same hazard was left unguarded in three other places that all read `res.timeS = W.t`. So a player who dies at 3:00 of a 12:55 standard match (storm table royale.js:250-260 sums to 775 s) and spectates to the end is shown "Survived 12:55" on the results screen — a visible lie — banks 193 survival XP instead of 45, and adds 775 s to career timeAliveS. ### [creatures-bots] Re-peeking a bot is free: reaction delay AND acquire overshoot both key off bb.acquireT, which is only stamped when the target ID changes
- **at** `runtime/3d/royale/bots.js:218`
- **why** Every humanising term in the aim model — the 210-700ms reaction delay and the 3x-decaying acquire overshoot — is a function of sinceAcq, and sinceAcq only resets when the bot switches to a DIFFERENT actor. Duck behind a wall for three seconds and step back out: perceive() re-finds you, `bb.target !== best.id` is false, acquireT is untouched, so sinceAcq is now 3.0 — acquireMul collapses to 1 and `reacted` is instantly true. The bot fires on the exact frame you become visible, at its full tier accuracy, with zero flinch. Line 212 compounds it: once you are bb.target the 160-degree vision cone is skipped entirely, so for a full 8 seconds the bot tracks you through 360 degrees and can pre-fire a peek from directly behind it. This is the single mechanic that makes an otherwise excellent brain read as a turret — first contact feels human, and every exchange after that in the same fight feels like an aimbot.
- **fix** Re-stamp acquisition on re-acquisition, not just on target switch. In perceive(), track `bb.lastSeenT` separately and add: `if (bb.target !== best.id || W.t - bb.targetSeenT > 0.35) { bb.target = best.id; bb.acquireT = W.t; }` — a third of a second of occlusion is enough to owe a fresh reaction. Scale the re-acquire cost below a cold acquire (e.g. `bb.acquireT = W.t - b.tierK.reactionMs/1000 * 0.5` on a re-peek within 2s) so repeated peeking degrades gracefully instead of resetting to a cold 700ms. Separately, gate line 212's cone bypass on recency: `bb.target !== t.id || W.t - bb.targetSeenT < 1.5`, so a sticky target you have genuinely lost no longer grants rear-arc vision.
- **vs benchmark** Apex/Warzone bot and low-MMR-player models charge a fresh (usually reduced) reaction cost on every re-exposure, which is exactly what makes cover-peeking a readable skill loop. Final Drop's bots are cruder overall but also lose track when you break LOS. Here, breaking LOS is strictly punished — the bot is MORE accurate on your second peek than your first.

### [creatures-bots] inp.sprint is dead code inside ENGAGE — inp.ads wins player.js's speed ternary, so bots close on you at 3.8 m/s, slower than a walking player
- **at** `runtime/3d/royale/bots.js:560`
- **why** ADS is tested BEFORE sprint in the speed ternary, and bots set ads=true for any engagement past 25m. Sprint only turns on past prefer*3, which is 90m for an AR, 42m for an SMG, 48m for a pistol, 270m for a sniper — every one of those thresholds sits above 25m, so whenever inp.sprint is true, inp.ads is also true and the bot is hard-capped at K.MOVE.ads = 3.8 m/s. inp.sprint in actEngage can therefore never produce a sprint for any weapon except the shotgun (prefer*3 = 21m). The result: a bot that spots you at 90m with an AR shuffles toward you at 3.8 m/s while the player walks at 6.0 and sprints at 9.6 — it can literally never catch you, and it looks like it is wading. Worse, it interacts with the fight-fatigue timer at bots.js:527 (`if (bb.fightT > 14 && ...)`): 45m of approach at 3.8 m/s takes 12s, so bots that spot you at medium range frequently hit the 14s stalemate timeout and wander off before they ever arrive. The same dead-sprint bug appears in the reload break at bots.js:553-558, which sets `inp.sprint = true` alongside `inp.mz = -0.5` — player.js:734 requires `inp.mz > 0.5`, so backpedalling out of a reload is also a walk.
- **fix** Do not ADS while repositioning. In actEngage, set ADS only when the bot is actually holding still enough to shoot: `inp.ads = dist > 25 && !inp.sprint && Math.hypot(a.vel.x, a.vel.z) < 5;`, and set `inp.sprint = dist > prefer * 1.8` (not *3) so the closing phase is a real sprint. For the reload break at 553-558, either sprint away properly (`inp.mz = 1` toward cover, sprint true) or drop the sprint flag and stop claiming a sprint the movement code cannot honour.
- **vs benchmark** Every AAA BR bot and every human alternates: sprint to close, then hard-stop and ADS. Final Drop bots visibly sprint-rush. A bot that ADS-walks the entire approach at 40% of player speed is the classic 'turret on rails' read the whole brain was written to avoid.

### [creatures-bots] A bot at 59 HP pops an 8-second medkit and becomes a rooted, non-firing, non-abortable target — while the human can move freely while healing
- **at** `runtime/3d/royale/bots.js:147`
- **why** The common mid-game state — shield topped up, HP in the 50s, nobody shot at me for 6s — scores HEAL at 45, which beats LOOT (20 once upgraded) and WANDER (12). startHeal then picks medkit first whenever shield >= 40, committing to an 8-second channel. From that point the bot is frozen: think() early-returns at line 147 before the ENGAGE utility is even computed, so a player walking into view cannot change its mind; actHeal zeroes both movement axes; weapons.js:306 blocks all firing; and there is no cancellation path anywhere in the codebase (the only `a.healing = null` is the timer expiring). Eight seconds is longer than the entire 14s fight-fatigue window. In practice you find bots standing perfectly still in the open, arms down, and execute them for free. The asymmetry is the sharp part: player.js never gates movement on a.healing, so the HUMAN strafes around at full speed while chugging — only the bots root themselves, and only because their own actHeal tells them to.
- **fix** Two parts. (1) Pick the cheapest sufficient heal, not the biggest: in startHeal, if `a.hp >= 60` (bandage cap is 75) prefer bandage/mini_shield — reserve the 8s medkit for hp < 40. (2) Make the channel abortable and let the brain use that: add `W.cancelHeal = (a) => { a.healing = null; }` next to useConsumable in player.js:25, call it from hurtActor when `victim.healing` and the damage came from an actor, and change bots.js:147 to `if (a.healing) { if (bb.target && W.t - bb.targetSeenT < 0.5) { W.cancelHeal(a); } else { b.state = "HEAL"; return; } }`. Also let actHeal walk toward cover instead of hard-zeroing mx/mz — the movement code already permits it.
- **vs benchmark** Fortnite/Apex bots break line of sight before consuming and abandon the heal when pushed; Apex additionally cancels on damage. Standing motionless in the open for 8s with the gun holstered is not a behaviour any shipped BR bot exhibits.

### [textures-materials] Every character renders FULLBRIGHT and fully metallic — Meshy's emissive-albedo hack is never stripped, and glTF's metalness default of 1.0 is never overridden
- **at** `runtime/3d/royale/player.js:185`
- **why** All 50 actors are effectively unlit decals. They receive no sun direction shading and no shadow darkening on the channel that supplies ~all their visible color, so a player standing inside a building reads exactly as bright as one in open sun — the single worst thing you can do to target readability in a BR, and the opposite of Apex/Warzone where shade is cover. They also pop off the (correctly lit) world as flat cutouts, and with maps.js:270 forcing NoToneMapping plus bloom 0.14, the fullbright emissive blooms.

This also silently defeated an earlier fix. The comment block at player.js:164-176 documents the team fighting this exact symptom: "Tuned against a render of four actors sharing one skin: at sat 0.16-0.30 / lightness 0.82-0.94 they were still indistinguishable on screen even though the hex values differed." That is precisely what metalness=1 + white emissive predicts: `m.color` feeds a diffuse term multiplied by (1 - metalness) = 0, while the dominant emissive path is `emissive(1,1,1) x emissiveMap` and is never tinted. The team compensated by pushing saturation to 0.38-0.58 instead of removing the cause — so the 50-player lobby is both fullbright AND more garishly tinted than it needs to be.
- **fix** In the clone block at player.js:183-188, normalize the Meshy export before tinting:
        const m = o.material.clone();
        m.metalness = 0;                       // glTF default is 1.0; Meshy omits metallicFactor
        if (m.emissiveMap) { m.emissiveMap = null; m.emissive.setHex(0x000000); }  // Meshy self-illum preview hack
        m.side = THREE.FrontSide;              // GLB says doubleSided:true — 2x fragment cost x50 actors
        if (m.color) m.color.setHSL(hue, sat, lig);
Then re-tune the wash DOWN (sat ~0.15-0.25) — once color drives a real diffuse term it separates actors at far lower saturation, which is what the comment at 173-176 was originally reaching for.
- **vs benchmark** Final Drop and every AAA BR light characters with the same sun/shadow/ambient the world uses; shade-vs-sun is a readability and stealth channel. Fullbright characters are a mobile-shovelware tell.

### [textures-materials] BoxGeometry UVs are never rescaled per face, so one brick/panel texture spans a 0.22 m lamp pole and a 32 m overpass deck identically — ~145x texel-density swing
- **at** `runtime/3d/royale/maps.js:1038`
- **why** Texel density runs 256/0.22 = ~1163 texels/m on a lamp post versus 256/32 = 8 texels/m on the overpass deck — a 145x spread inside one merged mesh. Players see 7 cm bricks on street lamps, 0.4 m-wide bricks squeezed onto every 0.35-0.4 m wall-thickness edge (sub-centimetre, aliases to mush), and 10.7 m x 1.5 m 'bricks' smeared across the overpass and mall — the exact surfaces you spend the most time fighting on. The world reads as untextured flat color at POI scale while small props look noisy. The same defect hits the road/parking mesh (maps.js:576, 590 -> maps.js:1049 groundTex): a 15x13 m parking slab gets one tile while the terrain it sits on tiles every 8 m (maps.js:294, TILE = 8), so there is a visible density seam where the lot meets the ground.
- **fix** Rescale UVs inside addBox before the batch push, using a fixed meters-per-tile constant so density is uniform. BoxGeometry's uv attribute is 24 entries in face order +X,-X,+Y,-Y,+Z,-Z spanning (d,h),(d,h),(w,d),(w,d),(w,h),(w,h):
    const S = 2.0;  // meters per texture tile
    const uvA = geo.attributes.uv, sp = [[d,h],[d,h],[w,d],[w,d],[w,h],[w,h]];
    for (let f = 0; f < 6; f++) for (let k = 0; k < 4; k++) {
      const i = f * 4 + k;
      uvA.setXY(i, uvA.getX(i) * sp[f][0] / S, uvA.getY(i) * sp[f][1] / S);
    }
    uvA.needsUpdate = true;
Do it before `geo.rotateY(opts.rotY)` so rotated boxes stay correct. wrapS/wrapT are already RepeatWrapping (maps.js:78/89), so no other change is needed. Apply the same treatment in `road()` (maps.js:576) and `parkingLot()` (maps.js:590) with S = 8 to match the terrain's TILE.
- **vs benchmark** Uniform world-space texel density is table stakes — Final Drop's blockout props all share one density budget; UE/Unity BRs enforce it with a texel-density checker in CI. A 145x spread inside one material is the single most visible 'programmer art' tell in the render.

### [animation-rig] Every network-remote actor is permanently stuck in the jump clip — onGround is never replicated
- **at** `runtime/3d/royale/player.js:912`
- **why** netRemote actors never run stepActor, and net.js's packet (pack() at net.js:329) carries only pos/yaw/hp/shield/gliding/weapon. `onGround` therefore stays at its constructor value `false` forever, so the very first non-gliding frame syncObj runs for a peer it falls into the airborne branch and plays the 5.93s Meshy jump clip with `once:true` (clampWhenFinished). playAnim's same-key guard (player.js:272) then blocks every later call, so after ~4.2s the peer clamps on the jump clip's final frame and holds it for the rest of the match while sliding across the ground. Remote humans never walk, run, idle, crouch or backpedal. On a GUEST client this is not one player — ffg_royale3d.js:264 marks all 49 bots netRemote, so the entire lobby is a field of identical frozen statues skating over the terrain. `a.vel` is likewise never written, except by explosion knockback (weapons.js:600-603), which permanently poisons it: once a peer is caught in one grenade, `spd2 > 1.2` stays true forever and syncObj:876 locks their body facing to that stale blast vector instead of their transmitted yaw.
- **fix** Add locomotion state to the wire format: in net.js `pack()` send `g: a.onGround?1:0, sw: a.swimming?1:0, cr: a.crouching?1:0, vx/vz: a.vel.x/z` (2 extra bytes each at 12Hz), and in `applyRemoteState` set `a.onGround`, `a.swimming`, `a.crouching` and `a.vel.set(vx,0,vz)`. ### [performance] antialias:true allocates a 4x MSAA backbuffer that the scene never renders into, because everything goes through the bloom composer — the game pays for AA and still renders aliased
